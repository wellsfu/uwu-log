# 團滅原因分析 (Wipe Cause Analysis)

## Overview

WIPE 不等於 DEATH。單一死亡的死因判讀是 `.claude/skills/death-cause-analysis/SKILL.md` 的責任(查 `*_MECHANICS.md`,一個 clip 一個結論)。這份 skill 處理的是另一層問題:**整把團滅的根本原因**——RL 判斷這把沒救、直接重來的真正理由。這個理由常常發生在「最後一個死亡」**之前**:某個機制沒處理好,raid 已經事實上沒救了,後面陸續斷氣的那幾個人只是撐得比較久而已,不是根本原因。

**「團滅」也不一定代表機制上真的打不下去了**——很多時候是RL在早期損失一個關鍵角色(例如少了一個治療)之後,判斷繼續打下去沒有意義,主動決定重來,即使理論上隊伍還能繼續。這種情況下,真正的根本原因是「觸發RL決定重來的那個早期失誤」,不是「所有人最終耗盡血量」這件事本身;`final_wipe`那一群甚至可能只是隊伍不再認真處理機制、放著讓自己死掉的收尾動作,不是新的獨立死因。**團隊當下講出來的結論用詞,不管是具體技能名稱還是「Trash fight」這種籠統說法,只反映他們複盤當下花了多少力氣去查,不代表這把wipe真的查不出機制**——即使預期團隊講得很籠統,還是要把Step 1~6完整跑過一次、自己去查FFLogs死亡明細跟傷害數字;查到的結果如果比預期更精確,就用查到的具體結果,不要因為預期是籠統說法就自己也跟著打馬虎眼。只有在自己實際查完仍然找不到清楚機制時,才用Step 6的通用結論。

這份 skill 是通用的**查表流程**,不寫死任何一個副本的技能——跟 `.claude/skills/death-cause-analysis/SKILL.md` 分工方式一樣:知識放在對應副本自己的參考檔案裡(死因判讀是 `*_MECHANICS.md`,這裡是 `memory/encounters/<NAME>/WIPE_ANALYSIS.md`),流程寫在這份 skill 裡。跟 `*_MECHANICS.md` 一樣,`WIPE_ANALYSIS.md` 是**給所有分析這個副本的人共用的知識**,不是某個團隊自己的黑話/名單/特定一次report的答案——那些屬於團隊自己的分析紀錄(類比 `analysis.js`),不放進共用檔案。新增副本時只要照樣寫一份新的 `WIPE_ANALYSIS.md`(記錄這隻王的機制怎麼影響wipe判讀、FFLogs查表常見的弱訊號模式),不用改這份 skill。

`scrape.mjs` 把每場 pull 的死亡事件依時間分群(10秒內算同一群,見 `settings.gapSec`),並在 `clusterAndFilter()` 幫每一群標記 `reason`。這個標記是判斷wipe根本原因的起點,語意如下(對照 `scrape.mjs` 原始碼,不是猜的):

| `cluster.reason` | 產生條件 | 對wipe分析的意義 |
|---|---|---|
| `ok` | 不是這把最後一群,且該群1~3人死亡 | 個別失誤,raid當下撐過去了。真正死因交給 death-cause-analysis 逐clip判讀;但**如果死的是坦克或治療,即使只標`ok`,仍要當成後續連鎖的起點檢查**(見Step 4) |
| `ignored_tactical` | 命中 `config.json`/`data.js` 裡設定的 `ignoreGroups`(例如固定幾個人配合某個技能刻意同死) | 設計上就會死的人,不是失誤,絕對不是wipe主因 |
| `too_large` | 不是最後一群,且該群≥4人死亡 | **最重要的信號**——中途一次倒了一大群人,raid通常從這一刻起已經回不來了,即使又拖了幾秒到幾十秒才真正結束。這通常才是wipe的真正觸發點 |
| `final_wipe` | 純粹是這把pull裡**時間最後**的一群死亡,人數多寡完全不影響判定 | 只代表「這把打到這裡結束」,**不代表死因**。可能只剩1、2個人斷氣(其他人早就在更早的`too_large`群死光了),也可能是整團一起收尾 |

**同一個玩家在同一把pull裡可能出現在不只一群**(死亡→被複活→後面又死一次是正常現象),分群只是照死亡事件時間切,不是照「誰還活著」切,讀 `players` 陣列時不要假設它等於「當時的存活名單」。

## When to use

- 幫某晚raid整理每把pull的「wipe原因」給隊友複盤(對照 `death_clips/<日期>/data.js`)
- 被問「這把為什麼會團滅」、「這次wipe的原因是什麼」
- 想知道某把pull真正卡在哪個機制,而不是只看FFLogs標的最後一個死亡技能

## Step 0 — 查這個副本專屬的wipe參考檔案(如果有)

查 `memory/encounters/<副本代號>/WIPE_ANALYSIS.md`(例如 `memory/encounters/UWU/WIPE_ANALYSIS.md`)。這份檔案(如果存在)記錄這個副本的機制特性怎麼影響wipe根本原因判讀、FFLogs查表時已知的弱訊號模式(例如某些機制會讓FFLogs查不到致命技能名稱、或某段collapse其實是另一個機制流程的收尾而非phase欄位標的那個階段)。**這份檔案是給所有分析這個副本的人共用的,不含任何一個團隊自己的黑話、名單、或特定一次report的答案**——找不到這份檔案,或找不到符合當下情況的記錄,不代表不能分析,直接照Step 1~7的通用流程走,`conclusion`用當下觀察到的白話描述即可。

## Step 1 — 取出這把pull的完整cluster序列

從對應日期的 `death_clips/<日期>/data.js` 找到目標 `pullNumber`,依 `timeText` 順序列出它的 `phase`、`durationText`、`percent`(團滅時boss剩餘血量,可以幫忙判斷大概卡在哪個機制段落),以及每一群的:人數、`reason`、涉及哪些人/職業。

## Step 2 — 往回找真正的「觸發群」,不要預設是最後一群

由後往前掃這把pull的clusters:

1. **先看`final_wipe`前面連續幾群是不是都是`too_large`(中間沒有被`ok`/`ignored_tactical`隔開)。如果連續好幾群都是`too_large`,取這一串裡最早的那一群當觸發點**——後面的`too_large`/`final_wipe`通常只是「沒有奶/沒有坦之後」的連鎖收尾,不是新的獨立死因(例如:治療先在某個too_large群倒下,20幾秒後全團又在下一個too_large群或final_wipe被沒人加血/減傷的後續機制收掉——根本原因是第一群,不是第二群)。
2. **找不到`too_large`群**(這把只有一個cluster,或非最後群全部是`ok`/`ignored_tactical`):`final_wipe`本身就是要查的觸發事件,不管它是1個人還是8個人。
3. 決定觸發群之後,**回頭再看觸發群前面緊接著的1個`ok`小群**——如果那一群死的是坦克或治療,通常才是整條連鎖真正的起點(見Step 4),觸發群本身只是連鎖的第一個大規模結果。

**核心提醒**:`final_wipe`人數少不代表死因輕微,人數多也不代表就是根本原因所在的那一群——先跑完上面3步再下結論。

## Step 3 — 查機制,精確技能名稱要去FFLogs核對

用觸發群的`timeText`對照這把的`phase`,查這個副本根目錄的 `<副本代號>_MECHANICS.md`(例如 `UWU_MECHANICS.md`)找對應的機制段落。**有些副本後期階段會直接沿用早期階段的技能**,同一技能名稱不能只看FFLogs標的phase就假設是哪隻王本體放的,跟 death-cause-analysis 的Step 4完全一樣的警告;找不到對應的機制對照表,就照 death-cause-analysis 的做法,直接說明查無機制對照表,不要拿別的副本硬套。

**查機制表時不要只逐一比對單一技能名稱,要看觸發群的整串技能序列是否對得上機制表描述的「一整段流程」**——很多副本的機制表會把某個階段的技能序列寫成一整套固定流程,而這套流程收尾常常有一個關鍵的結算技能(通常是需要極限技/無敵/群體減傷才能擋下的全屏大招)。**機制表裡如果某個技能那一列已經寫好死因判讀(例如「需要開啟坦克三段極限技硬扛,否則團滅」這種文字),那就是現成答案,直接採用,不要自己另外編一個故事**(跟 death-cause-analysis Step 5 的優先順序邏輯一樣)。看到觸發群整段序列對得上這種收尾流程,即使死亡明細上實際出現的技能名稱是序列中較早的那幾個,也要往後查有沒有收尾的結算技能,不能查到序列前段的技能就停下來。

**`data.js`本身不含技能名稱**——`scrape.mjs`抓下來後,序列化進`data.js`之前特意把每個死亡事件的`abilityName`丟掉了,只留人名/職業/分群結果給網頁展示用,不是資料缺漏。要精確判斷觸發群裡每個人實際是被什麼技能打死的,去查這把的FFLogs報告(`fflogsUrl`)看死亡明細,不要憑phase時間區間用猜的當最終結論。有FFLogs API client(`config.json`的`clientId`/`clientSecret`)時優先用API批次查,比人工開很多分頁快且不會漏看跨行的技能名稱;沒有API存取時開`fflogsUrl`網頁人工查也可以。

**團隊口語講的技能名稱不一定是FFLogs死亡明細裡的字串,不同團隊的講法也可能不一樣**——用死者的職業/場上角色去推斷團隊黑話對應哪個實際機制,不要因為FFLogs欄位沒有逐字出現這個詞就判定兜不起來。Step 0的`WIPE_ANALYSIS.md`如果記錄了這個副本某些技能設計上容易被誤判的地方(例如某個機制的AOE設計上不會打到被點名的人本人),可以幫忙判斷團隊黑話實際指的是哪個機制。

## Step 4 — 判斷是不是連鎖失敗,別急著怪死者自己

檢查觸發群(以及Step 2.3提到的前一個小群)裡是誰:

- **坦克死在觸發群或其前一個小群**:查副坦有沒有在死亡後立刻接手嘲諷、把王的朝向/位置拉開——常見連鎖是「主坦倒下,副坦接仇但沒走位,球王的AOE朝向留在raid身上」
- **治療死在觸發群或其前一個小群**:後面若有其他人接著死,大概率是純粹沒奶而失血,不是又中了一個新機制
- **觸發群人數接近或等於全隊,且找不到單一坦克/治療死因當起點**:通常是raid-wide機制沒處理好(集合/分攤/走位未過點),不是某一個人的問題
- **點名/疊層類機制的死亡明細,被點名的那個人自己常常不在死亡名單裡**——這類機制常見設計是「被點名的人自己不會被自己的AOE打到,沒走位閃開的旁人才會」,所以查FFLogs時看到某個技能打死了好幾個人,要另外確認「誰是被這個機制點名疊層的人、她走位是否正確」,不能只看誰真的斷氣
- **另一種點名機制剛好相反:被點名的人自己會被打,而且通常設計上需要坦克主動站到她面前提供減傷/嘲諷保護,才能把傷害降到扛得住的範圍**——這種機制底下,死亡名單裡如果就是被點名的那個人自己(尤其是非坦克的治療/輸出),根本原因常常是「該負責掩護的坦克沒有站位/沒有及時提供減傷」,不是點名的人自己走位錯誤。查Step 3的機制表確認這個技能設計上是哪一種——被點名的人該自己閃開讓別人躲開,還是該有坦克來掩護她——兩種查起來的方向剛好相反,不要套錯

## Step 5 — 下結論前先挑戰自己:這筆傷害真的補得住嗎?

在把Step 2~4的推理寫成結論之前,反過來質疑自己剛推出來的說法——去查FFLogs這次死亡的實際傷害數字,跟隊伍當下的血量上限、可能的治療/減傷量比較:

- **傷害量遠超血量上限,補血/減傷本來就攔不住**:代表這是一擊必殺類機制(機制表通常會有專門分類),死因判讀不該停在「沒補到/沒站好」這種可以被健康池或治療彌補的說法。回頭確認這是不是某個「需要特定資源或動作才能擋下,不然必死」的門檻(常見於需要極限技、無敵、群體減傷才能擋下的機制,機制表通常會寫「否則團滅」)——這種門檻沒跨過,才是真正的根本原因,不是表面上「誰先倒下」這件事本身。
- **傷害量在可補血/可減傷的範圍內卻還是死了**:才是真正的「沒補到/機制沒躲開」的補量類死因,這時Step 2~4的推理才站得住腳。

**如果自我挑戰後發現原本的結論站不住腳(例如死因其實是某個門檻沒跨過,而不是誰的走位問題),回到Step 2/3/4重新找觸發群、重新查機制,不要因為已經寫出一個聽起來合理的故事就停止分析。**這一步跟Step 3的「查機制表整段流程收尾的結算技能」是同一件事的兩個角度——一個是從機制表反查,一個是從實際傷害數字反查,兩邊都要對得上才算真正驗證過。

## Step 6 — 沒有乾淨的單一機制時,用通用結論,不要硬掰

如果Step 3~5查完FFLogs仍然看不出明確單一機制(例如整把陸續好幾個`ok`小型死亡疊加、體力被磨光,或觸發群橫跨多個機制視窗查無定論),不要硬套一個聽起來合理但查無實據的技能名稱。用當下最貼切的白話說法即可(例如「整把打得亂,沒有單一機制可歸咎」),不需要是特定固定講法。**這種籠統結論本身就是有效分析,不是偷懶**——寧可承認查不到,也不要編一個假的機制名稱。

## Step 7 — 寫成三段式結果,比照 death-cause-analysis 的格式

跟 death-cause-analysis 一樣,每筆wipe分析寫成一個物件,固定三個欄位:

| 欄位 | 內容 |
|---|---|
| `conclusion` | 一句話,團隊慣用的簡短口語結論 |
| `mechanism` | 機制講解——觸發群對應的技能是什麼、怎麼運作;若Step 2判斷出是連鎖(先一個機制導致坦/奶倒下,再由後續機制收尾),兩段機制都要講 |
| `detail` | 詳細分析——結合這把實際的cluster時間點、人數,說明為什麼判定觸發點在這裡(而不是無腦指向`final_wipe`),以及Step 4的連鎖推理(誰先倒、為什麼後面的人跟著死) |

**跟 death-cause-analysis 一樣**:這三段文字是給隊友複盤看的最終結果,必須自成一體——不要提到`data.js`、`cluster.reason`、`too_large`/`final_wipe`這些內部欄位名稱,把判斷轉成白話文字(例如把「這是too_large群」寫成「這時一次死了4個人」)。`conclusion`維持簡短口語風格,用觀察到的白話描述,不要展開成正式技能全名的長句;有現成的團隊慣用語/職業簡稱就照團隊自己的講法寫,沒有就用中性的白話描述,不用刻意發明新詞。`mechanism`/`detail`可以完整講清楚,但不需要像death-cause-analysis逐clip分析那樣長。

若要留存紀錄,格式比照 `analysis.js`(key是`clipFile`),這裡key用`pullNumber`:

```js
window.WIPE_ANALYSIS = {
  6: {
    conclusion: "...",
    mechanism: "...",
    detail: "...",
  },
};
```

## Common mistakes

- 只看`final_wipe`那一群人數多寡就下結論,沒有往前檢查是否已經有更早的`too_large`群——最後死的人常常只是「已經沒救之後撐得比較久」而已
- 連續出現兩個`too_large`群時,只看最後一個,沒有往前找到連鎖真正開始的那一群
- 看到`too_large`群人數多就直接寫「全團」,沒有檢查是不是坦克/治療先倒導致的連鎖(Step 4)
- 憑phase時間區間硬猜技能名稱,沒有去FFLogs核對死亡明細就下結論
- 查無實據時硬要幫每把wipe都掰一個具體技能名稱,而不是老實用團隊已經在用的通用說法
- `conclusion`欄位寫成正式技能全名的長句,而不是團隊自己在用的簡短口語——`mechanism`/`detail`才是展開講清楚的地方
- 在`mechanism`/`detail`裡直接寫`data.js`/`cluster.reason`/`too_large`這些內部欄位名稱,而不是轉成白話文字——隊友看到的是複盤結論,不需要知道這些內部判斷用的資料結構
- 忽略Step 0——副本自己整理過的`WIPE_ANALYSIS.md`裡可能已經記錄某些技能設計陷阱或FFLogs查表的弱訊號模式,沒查就自己從頭摸索
- 查到一個技能名稱、講得通一個故事就停手,沒有做Step 5的自我挑戰——傷害數字明明大到補血/減傷本來就攔不住,卻寫成「沒補到」/「站位問題」這種可被彌補的說法,漏掉真正需要極限技/無敵才能擋下的門檻
- 機制表整段流程只查到序列前段出現的技能就停下來,沒有往後查有沒有收尾的結算技能(而那個結算技能那一列其實已經寫好死因判讀)
- 看到團隊自己當下的說法很籠統(例如「Trash fight」),就預設這把真的查不出機制而跳過Step 1~5自己去查——籠統說法常常只代表團隊複盤當下沒花時間細查,不代表機制真的查無實據;RL也可能是在早期損失關鍵角色後就直接決定重來,不用等到隊伍真的耗盡血量,根本原因要往前找那個早期失誤,不是照抄團隊當下的籠統結論
- 點名類機制查到「被點名的人自己就死在名單裡」時,直接套用「被點名的人自己走位錯誤」,沒有先查機制表確認這個技能是不是「需要坦克掩護,沒被掩護就會死」的相反類型
